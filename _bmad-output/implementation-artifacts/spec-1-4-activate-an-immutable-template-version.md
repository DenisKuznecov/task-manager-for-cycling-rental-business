## Intent

**Problem:** Admins and Managers can author a Draft but cannot make it the workshop standard. Future Bike Tasks have no immutable Active version to snapshot, and replacing an Active version is not an atomic, reviewable action.

**Approach:** On Draft detail, Activate opens a confirmation panel, then a privileged transactional capability locks the pairing, re-reads the Draft and current Active pointer, activates the selected version, supersedes any prior Active atomically, and records an attributed event. Success appears only after Library and detail reload authoritative status.

## Boundaries & Constraints

**Always:** Idempotent local-only migration. Activate only through a `SECURITY DEFINER` RPC that authorizes Admin/Manager, requires `status='draft'`, matches `expected_revision` and `expected_active_version_id` (null when none), takes `workshop_checklist:{category}:{phase}`, re-validates Item structure (M2→M1 and type/applicability), and commits Active + optional Supersede + one `activated` event together. Unique one-Active-per-template index remains the last line of defense. Empty Items are structurally valid. Missing Setup Category coverage never blocks; show it as non-blocking copy in the panel. Call from `withAuth`; return `{ ok, revision }` or `{ ok: false, error, stale?, revision?, status?, activeVersionId?, activeVersionNumber? }`; revalidate Library, activated detail, and superseded detail when present. Stale keeps the panel open and requires explicit Retry — no silent rebase. Pending stays on Activate; Saved/Active only after reload.

**Ask First:** Reactivation; copy-from-Active; Bike Task snapshots; Setup Category lookup table; changing `/workshop` dashboard access; table DML policies or service-role writes; migrating beyond local Supabase.

**Never:** No app-role version/item/event DML; no client role checks as authz; no mechanic/partner/anon/`PUBLIC` execute/write. Do not mutate Items during activation, edit Active/Superseded definitions, treat missing Setup Category coverage as a gate, claim success before the server result, or migrate staging/production. Do not implement Reactivate. Do not edit Story 1.1–1.3 migrations or `001`/`002`/`003` pgTAP files.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| First activate | Admin/Manager; valid Draft; no Active; current revision | Draft → Active; event; revision +1; detail reloads Active | N/A |
| Replace Active | Valid Draft; pairing already has Active | Selected → Active; prior → Superseded atomically; one Active remains | Unique index still holds |
| Empty Draft | Zero items, structurally valid | Activates; empty definition is allowed | N/A |
| Missing Setup Category links | Some/all setup categories unused | Panel shows non-blocking coverage copy; activation proceeds | N/A |
| Invalid structure | M2 without M1 or invalid type/applicability | No status/event change | Actionable errors; revision unchanged |
| Stale revision or Active pointer | `expected_revision` or `expected_active_version_id` mismatch | No write | `stale` + current revision/status/Active; Retry after review |
| Concurrent activate | Two confirms, same pairing | One commits; the other is stale | No two Actives |
| Unauthorized | Mechanic/Partner/anonymous | Nested route denied; no write | EXECUTE+RLS denial |
| Non-Draft | Active/Superseded detail, or RPC on non-Draft | No Activate control; RPC denies | No status change |

## Spec Change Log

## Design Notes

Active pointer is the unique partial index on `status='active'`, not a separate table — the RPC must re-read that row under the same pairing lock used by draft create/item writes. `expected_active_version_id` is required (null meaning "no Active") so replacing a different Active than the one shown is stale, not a silent supersede. One `activated` event on the newly Active row carries `superseded_version_id`; do not add a `superseded` event type in this story. Item RPCs already reject non-Draft, so immutability after activate is status + existing guards, not new Item DML. Coverage is display-only from `WORKSHOP_SETUP_CATEGORIES` vs item `setupCategory` values.
