## Intent

**Problem:** Admins and Managers can open a blank Draft but cannot define, order, or remove the Items that later Bike Tasks will snapshot.

**Approach:** On Draft detail, add, edit, reorder, and remove Items through privileged transactional capabilities that enforce M2-implies-M1, unique positions, and expected-revision concurrency. Active and Superseded remain fully readable and immutable.

## Boundaries & Constraints

**Always:** Idempotent local-only migration. Item writes only through `SECURITY DEFINER` RPCs that authorize Admin/Manager, require `status='draft'`, match `expected_revision`, lock `(bike_category, phase)`, increment revision, and write an attributed event atomically. Call from `withAuth`; return `{ ok, revision }` or `{ ok: false, error, stale?, revision?, status? }`; revalidate Library and detail. Load items ordered by `position`. Empty Items stay a valid definition. Client and RPC both reject M2 without M1. Setup Category is optional nullable constrained text and never a visibility or coverage rule. Reorder submits the full item-id sequence. Mutations show pending on the affected control only; Saved only after the new revision returns; stale keeps entered values and current revision/status with Retry.

**Ask First:** Copy-from-Active; activation/reactivation; Setup Category lookup table or Booqable values; drag-and-drop reorder; changing `/workshop` dashboard access; table DML policies or service-role writes; migrating beyond local Supabase.

**Never:** No app-role item/event/version DML; no Bike Tasks; no client aggregation or client role checks as authz. No mechanic/partner/anon/`PUBLIC` execute/write. Do not mutate Active/Superseded rows, silently merge stale edits, hide Items in accordions, require Setup Category coverage, claim success before the server result, or migrate staging/production. Do not edit Story 1.1/1.2 migrations or `001`/`002` pgTAP files.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Add/edit Draft Item | Admin/Manager; valid fields; current revision | Item persisted; event; revision +1; Saved after reload | N/A |
| M2 without M1 | Client or RPC save | No write, no event | Field-level copy; no revision change |
| Reorder | Full permutation of current item ids | Dense positions committed; event; revision +1 | Duplicate/missing ids → reject, no partial order |
| Stale revision | `expected_revision` ≠ current | No write | `stale`; current revision/status; values kept |
| Remove | Confirmed; current revision | That Draft item gone; event; revision +1 | Active/Superseded/other versions untouched |
| Active/Superseded | Detail open, or stale client calls RPC | Readable items in order; no edit controls | RPC denies write |
| Unauthorized | Mechanic/Partner/anonymous | Nested route denied; no write | EXECUTE+RLS denial |
| Empty Draft | Zero items, load ok | Empty-definition copy + Add Item | Loader failure: banner + Retry, not empty success |

## Spec Change Log

## Design Notes

Authenticated roles still have no table DML, so item mutations cannot use `insert({})`. Four RPCs match the four editor actions. Reorder takes the full id array and writes dense `1..n` so duplicate/missing checks are set equality, not deltas. Setup Category is constrained text (same pattern as phase/category), not a lookup table — the link is metadata only. Keyboard Move up/down satisfies accessible reorder without `@hello-pangea/dnd`. Stale results must carry current `revision` and `status` because `{ ok: false, error }` alone cannot retry without a silent reload-merge. `item_id` on events is unenforced so remove can delete the item after the event row is written.
