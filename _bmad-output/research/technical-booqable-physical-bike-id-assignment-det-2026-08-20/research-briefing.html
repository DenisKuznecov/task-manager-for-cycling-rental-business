Booqable physical bike ID assignment detection

Decision: Choose the smallest reliable mechanism for detecting physical bike assignment, removal, and replacement on reserved Booqable orders.

Build a snapshot reconciler

The current implementation already uses order.updated as a signal, then fetches the complete order instead of interpreting the webhook payload. Keep that flow. Add a staff-triggered Sync latest data from Booqable action that re-fetches relevant upcoming reserved orders, compares their current stock_items.id values with stored state, and creates or cancels bike tasks from the difference. Skip completed and cancelled orders.

  1. The v4 API exposes physical assignments through order-line planning relationships, although the complete include parameter value needs live verification [1].
  2. The retrieved official sources do not establish assignment-event coverage or delivery guarantees. Fresh verification did not reproduce the initial pass's order.updated finding [2]; the official Zapier material confirms only a broader Updated Order trigger [3].
  3. Human-readable stock identifiers are editable, making the API resource ID the safer identity key [5].
MVP decision: Use order.updated plus an explicit manual sync. Do not add automatic periodic polling. Task creation may wait until the webhook fires or staff run the sync action.

Recommended architecture

Medium-high: snapshot reconciliation Low: assignment webhook as sole trigger
  1. Reconcile and persist. Implement one idempotent reconcileOrder(orderId). Fetch current assignments, serialize per order, and persist the canonical assignment set or snapshot hash.
  2. Apply set-diff semantics. For previous set P and current set C, create tasks for C − P, cancel tasks for P − C, and retain tasks for P ∩ C. Replacement {A} → {B} cancels A and creates B; it never transfers A's history.
  3. Trigger and recover. Keep the existing order.updated handler: use the event only to identify the order, then fetch its authoritative API state. Add Sync latest data from Booqable for staff to reconcile relevant upcoming reserved orders on demand. Exclude completed and cancelled orders, prevent simultaneous runs, show the last successful sync time, and use the same reconciler for both paths.
  4. Handle failure. Paginate until exhaustion. Retry transient failures and HTTP 5xx or 429 responses with exponential backoff and jitter; honor Retry-After when present.

Use a uniqueness constraint equivalent to (booqable_order_id, stock_item_id, task_kind). This design preserves the rule that work history belongs to one physical bike.

Controlled tenant spike

Use a disposable order containing a trackable bike product. Capture each webhook request and its headers, body, delivery timestamp, and response attempts. Capture the API snapshot immediately and after 1, 5, and 30 seconds.

  1. Reserve the generic product without selecting a bike; confirm that the snapshot has no physical stock item.
  2. Assign bike A in the UI; record emitted topics and verify the v4 relationship path, complete include parameter, resource ID, and read-after-write lag.
  3. Remove A; verify {A} → ∅.
  4. Replace A with B; verify {A} → {B} becomes cancellation of A and creation of B.
  5. Repeat assignment, removal, and replacement through order_fulfillments/specify; compare UI and API behavior.
  6. Make an unrelated order edit; verify a broad update produces a no-op reconciliation.
  7. Perform rapid A → B → C; measure ordering, coalescing, stale payloads, and convergence.
  8. Cause a timeout and return HTTP 500 responses; measure retries, duplicates, identifiers, and authentication. Trigger API 429 separately.

Required outputs

  • Exact successful v4 relationship and include request.
  • Event behavior for every UI and API mutation.
  • Webhook retry, duplication, ordering, payload, and authentication behavior.
  • Measured read-after-write delay and chosen debounce window.
  • Manual sync request volume, duration, failure behavior, and any HTTP 429 responses.
  • Clear UI behavior for progress, last successful sync time, success, and failure.
Acceptance rule: Both order.updated and the manual sync must call the same idempotent reconciler and converge on the correct physical-bike assignment. A missing webhook is acceptable because staff can recover through manual sync.

Integration evidence

Snapshot reconciliation is feasible

Booqable distinguishes generic reservation from later selection of a specific physical item and supports removing selected items [4]. The v4 hierarchy is:

order
└── lines
    └── planning
        └── stock_item_plannings
            └── stock_item

The candidate nested request is:

GET /api/4/orders/{order_id}
  ?include=lines,lines.planning,
           lines.planning.stock_item_plannings,
           lines.planning.stock_item_plannings.stock_item

The complete dotted parameter remains unverified. Legacy v1 independently confirms the planning model but should not guide v4 compatibility [7]. Store stock_items.id as the safer identity key and the human-readable stock identifier as mutable display metadata [5].

Events cannot yet be authoritative

The retrieved official sources do not define whether UI or API assignment changes emit an event. The official Zapier article does not connect stock assignment to its Updated Order trigger [3]. A secondary OpenAPI extraction identifies POST /api/4/order_fulfillments/specify, useful for testing but not authoritative for webhook side effects [6].

The retrieved v4 page documents authentication, pagination, single-use signed requests, and HTTP 429, but it does not specify quotas, assignment payloads, webhook delivery behavior, event IDs, receiver authentication, read-after-write lag, or an assignment change feed [8].
