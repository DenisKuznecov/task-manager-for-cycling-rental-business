Final synthesis · accepted model

One bike.
One living record.

Not a mini order-management system. Not a frozen digital form. A task that translates rental intent into physical work, keeps independent verification honest, and stays with the bike until its rental-specific changes are addressed on return.

01

Living, not final

Reserved configuration may change. Before claim it refreshes silently; after work begins it selectively reopens affected work.

02

Honest responses

Action items use explicit Done or N/A. Value items require values and offer no N/A; optional values may remain blank.

03

Independent quality

M2 makes a fresh attestation, may correct the bike after speaking with M1, and records that correction in shared Notes.

04

Scoped memory

Notes follow this rental into return, but do not automatically become a cross-rental physical-bike history.

The build line · clearly bounded

First release earns trust
at the workbench.

The accepted MoSCoW boundary protects the two ideas that make the feature worth building: living Booqable-driven bike work, and rental-specific Notes carried into return.

MUST · FIRST RELEASE

The accepted product core

  • Booqable-driven per-bike task queues, ordered by rental start date
  • Versioned, category-specific Prep and Return checklist templates
  • Always-visible admin-authored Prep items with optional links to five setup categories
  • M1 preparation plus independently attributed M2 verification where configured
  • Action responses as Done/N/A; value responses as required or optional values
  • Automatic selective reopening when linked Booqable setup changes after work
  • Shared task Notes for rental-specific bike changes and M2 corrections
  • Return checklist triggered by Booqable returned status, with Notes acknowledgement
  • Attention and audit history; cancellation/removal preserved read-only

SHOULD · FOLLOW

Valuable, not release-defining

  • Manager at-a-glance counts and date-scope filters
  • Performance views using M1/M2 attribution
  • Changed-work visibility through normal task filtering
  • Broader workshop analytics after trusted usage data exists

WON’T · THIS RELEASE

Explicitly outside the boundary

  • Replace Booqable’s full order lifecycle
  • Cross-rental bike history or usage analytics
  • Offline mode and retained unsaved changes
  • Automatic mechanic assignment
  • Generated accessory checklist items
  • Shared Notes revision history
  • Bikefit cross-reference
  • Separate revalidation tasks, statuses, or manager ping flows

The idea parts bin

Useful roads
not taken.

These ideas shaped the accepted model by revealing complexity, false certainty, or a boundary better left for later. They are intentionally distinct from the final design.

Retired model

Generated accessory checklist items

Replaced by always-visible admin-authored items linked to bounded setup categories.

Rejected

Explicit “Release to workshop” gate

There is no real operational readiness moment; reserved tasks are living work that absorbs updates.

Simplified away

Changed / Revalidation pipeline

Changed work returns to ordinary Prep and Re-check queues on the same task.

Removed

Manager urgent ping

No special urgent-mark mechanism; reopened work follows the normal start-date-prioritized queue.

Rejected

Automatic assignment

The system cannot know real-world mechanic workload. Self-claim and explicit assignment remain.

Rejected

Accessory dependency bundles

Too impractical to map accessory changes reliably onto manually authored stable checks.

Rejected

Admin complete-without-check

Would undermine independent quality evidence. Reassignment is allowed; checking remains required.

Rejected

Separate accessory adjustment tasks

Would expand the task model; the existing bike task absorbs reopened setup work.

Deferred direction

Full bike identity history

Stock-identifier usage frequency, cumulative parts and modifications remain a separate future feature.

Deferred direction

Full order-lifecycle ownership

Booqable already works end-to-end. Replacing it is not the mechanics-workflow problem.

Deferred concern

Offline resilience

Unsaved markers and local retry were explored, then explicitly moved out of current scope.

Parked

Bikefit cross-reference

A potential connection to existing bikefit data, intentionally not needed now.

Whenever rental intent changes the physical bike, keep the difference actionable until a mechanic confirms the bike matches the required state.

That single rule connects setup changes, independent verification, shared Notes, and return restoration—without stealing ownership of the order lifecycle from Booqable.
